The runner lane

gh-paddock runs a private repo's Linux test and dev jobs on Fargate tasks in an AWS account of their own, billed per second. One listener reads GitHub's runner scale-set API and starts a single-use runner for each job. This page walks through the v1 design, one event at a time.

The parts

Scale sets named by role

Each served repo gets one scale set per pool, named for its role: <repo>-test for CI, <repo>-dev for the dev deploy and its E2E gate. Each pool belongs to one repo, and its runner group is open to that repo alone and closed to public repos. Which repos are served is configuration in the CI account, never a file in this repo.

Single-use runners

Every runner registers with a just-in-time config, takes one job and deregisters. A task never runs jobs from two repos or two pools, so one repo's code and credentials never share a task with another's.

Warm reuse within a pool

A task whose runner finished starts a fresh runner and waits 30 seconds for the next job from the same pool. A dev deploy and the E2E gate after it chain on one warm task.

Remove, then terminate

The listener removes an idle runner through the API before it stops the task. GitHub refuses the removal while the runner holds a job, so a job handed over at that moment is kept and finishes.

GitHub is the queue

No webhook and no queue of our own. Jobs wait in GitHub while no listener runs, and a new listener reads GitHub and ECS and carries on.

Only the listener holds the key

The GitHub App's key stays with the listener, which alone starts and stops tasks. A runner task reads only its own config.

Every task defaults to 2 vCPU and 8 GB, as GitHub's runners for private repos do, and carries its repo and pool as cost allocation tags. Each pool has a maximum; jobs past it wait in GitHub. From one month of a real repo's job timings, v1 is estimated to cut that repo's monthly CI spend by about half, after paying for gh-paddock itself.

Later, not in v1

The prod stage later

Prod keeps GitHub's runners in v1. Later: an on-demand pool with a fresh task for every job.

Runners started in advance later

One runner kept started per pool, and dependencies baked into the runner image, if the speed checkpoint calls for them.

EC2 pools later

EC2 capacity of any kind, ECS Managed Instances included.

Staying on GitHub

Jobs that need a Docker daemon, KVM or the Android SDK, macOS jobs, and public repos keep GitHub's runners.
